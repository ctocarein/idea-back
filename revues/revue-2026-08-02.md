## Constats détaillés (nouveaux)

### Principe 1 — Séparation en couches (écriture de statut hors dépôt)

#### 🟡 Mineur — `app/pitchsim/service.py:604-605` : le service écrit le statut directement sur le modèle au lieu de passer par le dépôt

À la fin de `deliberate`, la clôture de session mute le statut **en écrivant l'attribut du modèle dans le service** :

```python
# app/pitchsim/service.py:604-606
await self._set_phase(ps, orchestrator.PitchPhase.COMPLETED)
ps.status = PitchStatus.COMPLETED     # ← écriture directe du statut dans le service
await self.session.commit()
```

Or le **même fichier** dispose déjà d'un chemin propre via le dépôt, utilisé pour l'abandon :

```python
# app/pitchsim/service.py:400
await self.repo.set_status(ps, PitchStatus.ABANDONED)   # ← via le repository (bon patron)
```

```python
# app/pitchsim/repository.py:93
ps.status = status
```

Le flux attendu est `service → repository` pour toute écriture. Ici la clôture court-circuite le dépôt et manipule la colonne à la main — une **incohérence de couche visible dans le même fichier** (comme l'écart `transition_review`/`assign_project` relevé le 08-01 dans `projects/router.py`). Le risque métier est **faible** : l'état réellement gouverné est la **phase** (`ps.phase`), et celle-ci est mutée exclusivement via `_set_phase(...)` qui garde chaque transition par `assert_transition` (cf. points conformes) ; `status` n'est qu'un miroir grossier (IN_PROGRESS/COMPLETED/ABANDONED) sans machine à états propre.

**Correction :** router l'écriture de clôture par `await self.repo.set_status(ps, PitchStatus.COMPLETED)`, comme l'abandon. Trivial, purement cohérence de couche.

### Principe 3 — Tout I/O externe est faillible (mode dégradé LLM)

#### 🟡 Mineur — `app/pitchsim/service.py:588-604` : la délibération multi-LLM n'a pas de mode dégradé (asymétrie avec `studio`)

Le endpoint `POST /sessions/{id}/deliberate` (`router.py:176`) déclenche `deliberate` (`service.py:570`), qui exécute **inline dans la requête HTTP** toute la délibération du comité : tour libre, puis **un appel LLM par persona** (boucle `:588-598`) pour les verdicts VERBATIM, puis le scoring (`_score`). Contrairement à `studio` — qui, en cas d'échec LLM, **dégrade** vers un lot déterministe (`default_variations`, cf. `revue-2026-08-01.md`) — cette boucle **n'a aucun `try/except` ni mode dégradé** :

```python
# app/pitchsim/service.py:594-598
for p in personas:
    prompt = build_verdict_prompt(...)
    if slide_images and hasattr(self.provider, "analyze_json_with_images"):
        raw = await self.provider.analyze_json_with_images(prompt, images=slide_images)  # ← nu
    else:
        raw = await self.provider.analyze_json(prompt)                                    # ← nu
```

Le provider LLM est **résilient** (timeout/retry/circuit breaker — voir `openai_compatible.py`, confirmé exemplaire le 08-01), donc les erreurs *transitoires* sont rejouées. Mais une erreur **permanente** (4xx `LLMError`, ou breaker **ouvert** après 3 échecs) **remonte l'exception et fait échouer toute la délibération à mi-parcours** : l'utilisateur perd l'intégralité des verdicts déjà obtenus et doit tout relancer. La transaction n'étant committée qu'en `:606`, l'état DB reste cohérent (rollback) — mais l'**expérience** est « tout ou rien », là où `studio` garantit toujours un résultat.

Ce constat **renforce le point ouvert #11** (« génération LLM inline dans la requête » — `pitchsim` y est déjà cité) ; l'**angle nouveau** est l'**asymétrie de robustesse** : `studio` dégrade, `pitchsim` non. S'agissant d'un traitement **lourd et faillible** (N appels LLM + vision), le référentiel (Principes 3 & 4) le destinerait idéalement à la **file de jobs** plutôt qu'à la requête HTTP.

**Correction (par ordre de coût) :** a minima, encapsuler chaque verdict dans un `try/except` avec un verdict de repli neutre (« indisponible », vote `conditional`) pour ne jamais perdre les verdicts déjà rendus ; idéalement, basculer la délibération complète en job asynchrone (table `jobs`) avec statut/`error_message` et reprise. Sévérité *mineure* (compromis UX assumé, appels déjà gardés côté résilience), mais c'est la seule branche de génération inline **sans** filet de dégradation.
