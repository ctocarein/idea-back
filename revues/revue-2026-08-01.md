## Constats détaillés (nouveaux)

### Principe technique — Autorisation cohérente (SEC / §5.4 « avoir la permission ne suffit pas »)

#### 🟡 Mineur — `app/projects/router.py:48-56` : mutation d'état gardée par une permission de lecture

Le handler `transition_review` **change le statut de curation** d'un projet (`new_diagnostic → in_review → qualified/needs_work/rejected → excellence`) — une **écriture** avec effet métier — mais il est gardé par une permission **de lecture** :

```python
# app/projects/router.py:48-56
@router.patch("/{project_id}/review-status", response_model=ProjectAdminOut)
async def transition_review(
    ...
    ctx: AuthContext = Depends(require(Permission.PROJECT_READ_ANY)),  # ← lecture
    ...
):
    return await svc.transition_review(ctx, project_id, body.target)
```

Or l'énum expose déjà une permission **dédiée aux transitions**, sémantiquement correcte :

```python
# app/iam/permissions.py:21
PROJECT_TRANSITION = "project:transition"  # déclencher une transition de statut
```

`PROJECT_TRANSITION` est aujourd'hui attribuée au **porteur** (pour soumettre son propre diagnostic), et il n'existe **aucune permission admin dédiée à la curation** — d'où l'usage par défaut de `PROJECT_READ_ANY`. Le service fait bien son travail (machine à états `can_transition_review` + audit atomique, cf. points conformes) ; le problème est **strictement au niveau de la garde HTTP** : une mutation gouvernée par un droit de lecture. Concrètement, dès qu'un futur rôle recevra `PROJECT_READ_ANY` à des fins de **consultation/triage** (analyste, support, dashboard interne), il héritera **silencieusement** du droit de curer les projets.

**Correction :** introduire une permission admin explicite (ex. `PROJECT_CURATE` / `PROJECT_REVIEW_MANAGE`) attribuée au rôle admin, et l'exiger sur `transition_review` à la place de `PROJECT_READ_ANY`. À aligner avec `assign_project` (`:59-67`) qui, lui, exige déjà correctement `USER_MANAGE` — donc l'écart est visible dans le même fichier. Sévérité *mineure* (périmètre admin-only aujourd'hui), mais à traiter avant tout élargissement de rôle.

### Principe 1 — Séparation en couches (lecture repo dans le router)

#### 🟡 Mineur — `app/projects/router.py:70-78` : le router lit le dépôt d'audit sans passer par un service

Le handler `project_timeline` injecte **directement** un `AuditRepository` et exécute la requête dans le router :

```python
# app/projects/router.py:70-78
async def project_timeline(
    project_id: UUID,
    ctx: AuthContext = Depends(require(Permission.AUDIT_READ)),
    audit: AuditRepository = Depends(get_audit_repo),  # ← repo injecté dans le router
) -> list[AuditLogOut]:
    rows = await audit.list_for_entity("project", project_id)  # ← lecture repo dans le handler
    return [AuditLogOut.model_validate(a) for a in rows]
```

Le flux attendu est `router → service → repository`. Ici le router **court-circuite la couche service** et parle directement au dépôt. C'est une **lecture pure** (best-effort, aucune règle métier, aucune écriture), donc un **faux positif partiel** au sens du risque — mais c'est la **même famille** que les points ouverts #2/#3/#10 (repos/services instanciés ou consommés dans des routers) et cela nuit à la cohérence : la timeline gagnerait à passer par un `AuditService.list_for_entity(...)` (ou une méthode du `ProjectAdminService`), ne serait-ce que pour centraliser un jour la pagination/filtrage.

**Correction :** exposer la lecture via une méthode de service (`AuditService`/`ProjectAdminService`) et injecter le service, comme le reste du fichier (`get_project_admin_service`). Trivial, purement cosmétique côté sécurité.
