## Constats détaillés

### Principe 6 — Tout est traçable

**🟠 Important — `set_visibility()` mute la visibilité sans trace d'audit**
`app/sharing/service.py:87‑93`

Rendre un projet public ou privé est une action sensible (exposition du projet aux
mentors/financeurs). Or `set_visibility()` écrit `is_public` puis `commit()` **sans**
`AuditService.record(...)`. Cela viole le principe 6 (« action sensible → `audit_logs`,
dans la même transaction que l'action »). Le codebase applique déjà ce pattern pour les
autres mutations d'état projet : `ProjectAdminService.transition_review` enregistre
`project.review_status`, `assign` enregistre `project.assignee`
(`app/projects/service.py:63,86`).

*Cause racine :* `ShareService` n'a pas d'`AuditService` injecté (voir son `__init__`,
`app/sharing/service.py:34`), contrairement à `ProjectAdminService`.

*Correction :* tracer, dans la même transaction que la mutation et avant `commit()` :
```python
await self.auditor.record(
    actor_id=ctx.user.id,
    action="project.visibility",
    entity="project",
    entity_id=project_id,
    old_value={"is_public": project.is_public},
    new_value={"is_public": is_public},
)
```
Le plus propre est de déporter cette logique dans un service projets (cf. 🟡 ci‑dessous),
qui possède déjà l'auditor.

### Principe 2 / cohésion des features

**🟡 Mineur — la mutation d'un attribut `Project` vit dans la feature `sharing`**
`app/sharing/service.py:87‑101`

`set_visibility` / `get_my_project_visibility` mutent et lisent l'état du domaine
**projet** (`is_public`) depuis la feature `sharing`. Le propriétaire naturel de l'état
projet est `app/projects/` (`ProjectAdminService`), qui a déjà `AuditService` injecté.
Les couches restent correctes (router → service → repository, pas de SQL dans le router),
c'est un problème de **cohésion de feature**, pas de saut de couche.

*Correction :* déplacer ces deux méthodes dans un service `projects` (ou un
`ProjectOwnerService`). Bénéfice double : la trace d'audit du 🟠 devient naturelle
(auditor déjà présent) et la visibilité redevient une affaire du domaine projet.

### Principe IAM — permission cohérente avec l'action

**🟡 Mineur — un PATCH mutant est gardé par une permission de *lecture***
`app/sharing/router.py:47‑62`

`PATCH /projects/{id}/visibility` (mutation) et `GET /me/project-visibility` sont tous
deux gardés par `Permission.REPORT_READ_OWN`. Ce n'est pas une faille — l'accès réel est
verrouillé par `guard_owner_access` (owner‑only) — mais le gate de permission est
sémantiquement faux : une écriture doit exiger une permission d'écriture.

*Correction :* le PATCH doit exiger `Permission.PROJECT_WRITE_OWN` (déjà défini,
`app/iam/permissions.py:20`) ; le GET est mieux servi par `Permission.PROJECT_READ_OWN`
(`:17`) que par `REPORT_READ_OWN`.

### Robustesse produit

**🟡 Mineur — `get_latest_for_owner` suppose « 1 porteur = 1 projet »**
`app/projects/repository.py:96‑101`, exposé par `GET /me/project-visibility`

L'endpoint renvoie la visibilité du **projet le plus récent** du porteur
(`order_by(created_at.desc()).limit(1)`). Si un porteur détient plusieurs projets,
l'endpoint devient ambigu (il ne dit pas de quel projet il parle). Acceptable si le
produit garantit un projet unique par porteur au stade MVP, mais à documenter/verrouiller
côté produit sinon. Note produit, pas un défaut de code.
