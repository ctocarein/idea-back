## Constats détaillés (nouveaux)

### Principe 4 — Tout traitement lourd/faillible passe par la file de jobs, jamais dans la requête HTTP

**🟠 Important — `app/pitchsim/router.py:196-208` : PDF post-mortem généré en synchrone dans le handler HTTP, bloque l'event loop.**

`GET /pitchsim/sessions/{id}/post-mortem/pdf` appelle `render_postmortem_pdf(html)` (l.205)
**directement, sans `asyncio.to_thread(...)`**. `render_postmortem_pdf` exécute
`weasyprint.HTML(...).write_pdf()` (`app/pitchsim/pdf.py:72`), une opération CPU-lourde et
**synchrone bloquante**. Dans un handler `async`, cet appel **gèle la boucle d'événements** pour
toute la durée du rendu : aucune autre requête n'est servie pendant ce temps.

Double violation du principe 4 : (a) un traitement lourd (rendu PDF) vit **dans la requête HTTP**
au lieu de la file de jobs ; (b) même à défaut de le sortir de la requête, il n'est pas déporté
dans un thread. Le contre-exemple exemplaire est **dans le même codebase** :
`app/diagnostics/handlers.py:149` fait `pdf_bytes = await asyncio.to_thread(render_bilan_pdf, html)`
**et** tourne dans le worker (job), **et** enveloppe le tout dans un `try/except Exception` de
dégradation gracieuse (`handlers.py:155`). Le doc d'archi est explicite : « Tout traitement lourd
ou faillible (analyse LLM, email, **PDF**) passe par la file de jobs, jamais dans la requête HTTP. »

Accessoirement, le handler ne rattrape que `ImportError` (WeasyPrint absent → 503) ; toute autre
défaillance de rendu (fonts, ressource) remonte en 500 non maîtrisé, alors que la version
`diagnostics` capture `Exception` largement.

*Correction (par ordre de préférence) :*
1. Déporter la génération dans un **job** (table `jobs`) : la route déclenche le job et renvoie
   l'URL presigned une fois le PDF prêt (schéma identique au bilan diagnostic).
2. A minima, si le PDF synchrone est conservé au stade MVP : envelopper dans
   `await asyncio.to_thread(render_postmortem_pdf, html)` **et** élargir le `except` à `Exception`
   pour une dégradation propre.

### Principe 2 — Séparation en couches (`router → service → repository → DB`)

**🟠 Important — `app/scoring/governance.py:43-61` : le router orchestre repo + audit + commit et instancie les dépendances en ligne.**

Le handler `activate_grid` (POST `/admin/scoring/grids/{version}/activate`) fait, **dans la couche
HTTP**, tout le travail d'un service :

```python
repo = ScoringRepository(session)                 # instanciation en ligne (pas de Depends)
grid = await repo.get_by_version(version)
if grid is None: raise NotFoundError("scoring_grid")
await repo.activate(grid)                          # mutation
await AuditService(session).record(...)            # audit instancié en ligne
await session.commit()                             # transaction portée par le router
```

Trois écarts au principe 2 : (a) `ScoringRepository(session)` et `AuditService(session)` sont
**instanciés en ligne** au lieu d'être injectés via `Depends(get_*_service)` ; (b) le router
**orchestre repo + audit + commit** — c'est le rôle du service ; (c) la **transaction** (`commit`)
appartient au service, jamais au router. C'est le même anti-pattern que `app/jobs/router.py` (déjà
signalé), mais ici l'enjeu est plus élevé : **activer une grille Radar ré-étalonne le scoring de
tous les projets** — une action d'administration parmi les plus sensibles du produit.

L'audit lui-même est présent et transactionnel (bon point), mais il est au mauvais endroit.

*Correction :* créer un `ScoringGovernanceService` (auditor + repo injectés) exposant
`activate_grid(ctx, version)` qui porte la logique et le `commit()`, et le câbler via
`get_scoring_governance_service` dans le handler, sur le modèle de `ProjectAdminService` /
`mentors`. Le handler se réduit alors à `return await svc.activate_grid(ctx, version)`.

### Principe 3 — Tout I/O externe est faillible

**🟡 Mineur — `app/reports/pdf.py:369-371` (et `app/pitchsim/pdf.py`) : WeasyPrint fetche des polices externes sans timeout.**

Le HTML des bilans référence Google Fonts via `<link href="https://fonts.googleapis.com/css2?...">`
(preconnect + stylesheet). Au rendu, WeasyPrint **résout et télécharge** ces ressources externes
par son URL-fetcher par défaut, **qui n'impose aucun timeout**. Un `fonts.googleapis.com` lent ou
injoignable peut donc **allonger, voire suspendre** le rendu PDF — un appel réseau sortant sans
garde-fou (principe 3). Pour le bilan diagnostic, l'impact est amorti (rendu en job + `try/except`),
mais pour pitchsim il se cumule avec le 🟠 ci-dessus (blocage synchrone dans la requête).

*Correction :* soit **embarquer les polices en local** (`@font-face` + fichiers `woff2` servis
depuis l'app, self-host) — élimine tout I/O réseau au rendu, recommandé pour un PDF déterministe ;
soit passer un `url_fetcher` custom à `HTML(...)` avec timeout court et fallback police système.
