## Constats détaillés (commits 24 h)

### Principe 2 — `core` technique / features métier

🟡 **`app/core/email.py:43-73`** — `send_verification_email` embarque désormais un dictionnaire de **gabarits bilingues user-facing** (`_VERIFY_EMAIL` fr/en : sujet + corps rédigés) dans `app/core/`. Le transport SMTP est bien technique (sa place est en `core`), mais le **contenu localisé destiné à l'utilisateur final** relève de l'i18n produit — l'archi (§0) demande que les messages utilisateur soient « gérés via i18n, pas en dur dans la logique ». Placement borderline, hérité (la fonction préexistait en `core`).
*Correction suggérée :* externaliser les libellés dans un catalogue i18n (ou `app/iam/`), ne garder en `core/email.py` que le transport et la signature `send_email(...)`.

### Principe 3 / robustesse des entrées — `currency` injecté dans le prompt

🟡 **`app/diagnostics/schemas.py:99` + `app/diagnostics/router.py:88` + `app/llm/prompt.py:59`** — le champ `currency` est concaténé **tel quel** dans le prompt d'extraction (`"…exprime-le en " + currency`). Or il n'est que faiblement contraint :
- via `IdeaExtractIn` : `Field(default="XOF", max_length=8)` — **pas de pattern** ;
- via l'endpoint fichier `extract_file_idea` : `currency: str = Form(default="XOF")` — **aucune validation** (ni longueur, ni pattern).

`lang` est correctement borné (`pattern="^(fr|en)$"`), mais `currency` ouvre une petite surface d'**injection de prompt / contenu parasite** (chaîne arbitraire poussée dans l'appel LLM). Risque faible (chaîne courte, provider tolérant) mais gratuit à fermer.
*Correction suggérée :* borner à un code ISO 4217 — `pattern="^[A-Z]{3}$"` sur `IdeaExtractIn.currency` **et** normaliser/valider le `Form` de `extract_file_idea` (whitelist ou même pattern) avant de le passer au service.
