## Constats détaillés

### Principe 4 — Tout est traçable

#### 🟠 `app/documents/service.py:80-93` — suppression de document sans audit
`delete(ctx, document_id)` retire l'objet MinIO (best-effort) puis supprime les métadonnées (`repo.delete(doc)` + `session.commit()`) **sans `AuditService.record`**. Une suppression de donnée utilisateur est une action sensible qui doit être traçable.

> Principe violé : « action sensible (… suppression …) sans `AuditService.record` dans la MÊME transaction que l'action ».

Contre-exemple conforme dans le même domaine : `app/gdpr/service.py:96` — `delete_me` enregistre `user.deleted` **avant** le commit (« l'audit survit à la suppression »). Le module documents devrait faire de même.

**Correction :** injecter `AuditService` dans `DocumentService.__init__`, et dans `delete`, appeler `await self.auditor.record(actor_id=ctx.user.id, action="document.deleted", entity="document", entity_id=doc.id, old_value={"object_key": doc.object_key})` avant `session.commit()`.

#### 🟠 `app/opportunities/service.py:85 / 99 / 119` — mutations admin de configuration sans audit
`admin_create` (:85), `admin_update` (:99) et `admin_set_active` (:119) committent des changements de configuration **effectués par un admin** (création/édition d'une opportunité présentée aux fondateurs, activation/désactivation) **sans aucun audit**. Le service n'injecte d'ailleurs même pas d'`AuditService` (aucune référence à l'audit dans tout `app/opportunities/`).

> Même famille de problème que l'activation de grille Radar signalée le 2026-08-03 (`scoring/governance.py`) : une **modification de configuration sensible** par un admin doit être tracée.

**Correction :** injecter `AuditService` dans `OpportunityService`, et enregistrer `opportunity.created` / `opportunity.updated` / `opportunity.activated|deactivated` dans la même transaction que chaque mutation, avant le `commit()`.

*Note :* `express_interest` (:127) émet bien une **télémétrie** (`instrumentation.emit(OPPORTUNITY_INTEREST, …)`) ; c'est de l'analytique, pas de l'audit, mais l'action (un fondateur exprime un intérêt) est à faible enjeu et n'exige pas d'audit formel — acceptable.

### Principe 3 — Tout I/O externe est faillible

#### 🟡 `app/documents/service.py:62,66,69,88` — consommateur du client MinIO non résilient (point structurel déjà ouvert)
`confirm_upload` (`stat_object`, `remove_object`) et `delete` (`remove_object`) appellent directement le client MinIO, qui — comme signalé le 2026-08-03 (`app/core/storage.py`) — n'a **ni timeout ni retry ni circuit breaker**. Les appels sont ici encapsulés dans des `try/except` (dégradation gracieuse correcte côté logique), mais un MinIO **injoignable/lent** peut bloquer la requête HTTP jusqu'au timeout par défaut d'urllib3. Ce n'est pas un nouveau défaut : c'est un **consommateur** du point structurel MinIO déjà ouvert. À traiter à la racine dans `app/core/storage.py`.

## Points conformes (rotation du jour)

- **Mentors — exemplaire (Principes 1, 4, 8).** `approve` / `reject` / `set_mentor_status` (suspend/activate) / `accept_invitation` s'exécutent **tous dans la couche service**, avec **garde d'état** (`BusinessRuleError` si « Candidature déjà traitée »), **audit transactionnel** (`mentor.approved`, `mentor.rejected`, `mentor.suspended|activated`, `invitation.accepted`) et `commit` en fin. Le **token d'invitation est hashé** (`_hash_token` / SHA-256), jamais persisté en clair — bon contre-exemple au point ouvert #13 (`app/sharing`).
- **Documents — pattern presigned propre.** L'API ne transporte jamais les octets (`presigned_put`), le `storage` est **injecté** (testable sans MinIO), et la confirmation applique la vérif SEC-06 (taille max + content-type autorisé, avec nettoyage de l'objet si refus). Dégradation gracieuse si storage non configuré.
- **Opportunities — layering + déterminisme.** Éligibilité **déterministe, sans LLM** (« reproductible »), aucune requête SQL dans le router, DI propre (`Depends(get_opportunity_service)`), `express_interest` garde la propriété du projet (`guard_owner_access`).
- **Séparation en couches (Principe 2).** `studio/router.py` et `pitch/router.py` — **faux positifs** du scan (`svc.select(...)`, `extract_text(...)`), aucune fuite SQL réelle ; DI propre via `Depends(get_*_service)`. `notifications` : `mark_read` / `mark_all_read` / `create` propres, aucun I/O externe.
- **Migrations réversibles.** 16 révisions Alembic (`alembic/versions/`), **toutes** avec `downgrade`.
