## Constats détaillés (nouveaux)

### 🟠 Principe 4 & 3 — Export du pitch : traitement lourd dans la requête HTTP + convertisseurs synchrones bloquants

**`app/pitch/service.py` `export_pitch` (l.157-195)**, exposé par **`GET /pitch/{pitch_id}/export`**
(`app/pitch/router.py:152-160`).

Deux violations cumulées, sur le modèle de ce qui a déjà été relevé pour le PDF pitchsim (07-02) et
les I/O MinIO/SMTP (07-03/07-04) :

1. **Traitement lourd hors file de jobs (principe 4).** L'export s'exécute **intégralement dans la
   requête HTTP** : lancement d'un **Chromium headless via Playwright** (`render_deck_pdf` /
   `render_deck_pptx`, `deck_export.py:28` `pw.chromium.launch()`) ou conversion WeasyPrint/pptx.
   Le principe 4 est explicite : « tout traitement lourd ou faillible (analyse LLM, email, PDF)
   passe par la file de jobs, jamais dans la requête HTTP ». Même sur le chemin `async` du deck
   (qui, lui, ne gèle pas l'event loop), la **connexion HTTP reste monopolisée** le temps complet
   du rendu Chromium — coûteux et faillible.

2. **Convertisseurs synchrones bloquants dans un handler `async` (principe 4 — event loop).** Sur le
   chemin de **repli texte** (`has_deck` faux) :
   - `app/pitch/service.py:183` → `render_pitch_pdf(...)` = **WeasyPrint synchrone** (`export.py:49`,
     `HTML(...).write_pdf()`), appelé **sans `await asyncio.to_thread`** ;
   - `app/pitch/service.py:189` → `render_pitch_pptx(...)` = **python-pptx synchrone**
     (`export.py:56`), même problème.

   Ces appels **gèlent la boucle d'événements** pour toute leur durée — exactement l'anti-pattern
   déjà signalé. Le contre-exemple exemplaire est dans le même codebase :
   `app/diagnostics/handlers.py:149` fait `await asyncio.to_thread(render_bilan_pdf, ...)`, et
   `app/reports/service.py:123` fait `await asyncio.to_thread(storage.presigned_get, ...)`.

**Correction suggérée :**
- Cible architecturale (principe 4) : **enfiler un job `export_pitch`** (table `jobs`) et renvoyer
  au client un statut / une URL de récupération signée une fois le rendu prêt (même contrat que le
  bilan PDF, produit hors requête). Cela résout aussi la monopolisation de connexion.
- À court terme, a minima envelopper les convertisseurs synchrones :
  `await asyncio.to_thread(render_pitch_pdf, html)` et
  `await asyncio.to_thread(render_pitch_pptx, pitch, project_title=title)` — cohérent avec le reste
  du code.

### 🟡 Principe 4 — `build_pptx_from_pngs` synchrone (CPU) dans une coroutine

**`app/pitch/deck_export.py:65,86-89`**

`render_deck_pptx` (async) capture les slides via Playwright (async, OK) puis appelle
`build_pptx_from_pngs(pngs)` — une fonction **synchrone python-pptx** (assemblage + `prs.save`) —
**directement, sans `to_thread`** (l.89). L'assemblage d'un petit deck reste rapide, d'où 🟡, mais
il **bloque l'event loop** le temps de la sérialisation. À traiter naturellement si l'export bascule
vers la file de jobs (cf. constat 🟠).

**Correction suggérée :** `return await asyncio.to_thread(build_pptx_from_pngs, pngs)`.

### 🟡 Principe 3 — Rendu Playwright sans timeout global ni circuit breaker

**`app/pitch/deck_export.py:22-51`**

`_open_deck_page` lance Chromium (`launch()`, l.28), charge le HTML (`set_content(wait_until="load")`,
l.30) et rend le PDF (`page.pdf()`, l.43) **sans timeout explicite** ; seul `wait_for_selector` est
borné (5 s, l.33, en best-effort). Un Chromium lent à démarrer ou une page qui ne finit pas de
charger peut donc **retenir la requête indéfiniment**. Le principe 3 impose timeout + retry/backoff
+ circuit breaker (`app/core/resilience.py`) sur tout traitement externe/faillible ; ici seul le
**mode dégradé** est présent (ImportError Playwright → 503 côté appelant). Sévérité 🟡 : l'export est
optionnel et déclenché explicitement par le porteur.

**Correction suggérée :** poser un `timeout` sur `launch()`/`set_content`/`pdf()` (Playwright accepte
`timeout=` par opération, ou `page.set_default_timeout(...)`), et — si l'export devient un job —
lui appliquer le statut/retry de la file. Optionnellement, envelopper dans le circuit breaker de
`app/core/resilience.py` au même titre que `app/llm`.
