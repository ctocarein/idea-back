## Constats détaillés

### 🟠 Important

#### 1. `app/jobs/router.py` — le router saute la couche service (principe 1)

Le router de supervision des jobs accède **directement au repository** et, pour la
relance, **orchestre lui-même repository + audit + transaction** — ce que l'architecture
réserve explicitement au service (« la transaction et l'audit appartiennent au service,
jamais au router »). Un `JobService` existe pourtant déjà (`app/jobs/service.py:25`)
mais n'est pas utilisé ici.

- `app/jobs/router.py:28` — `list_jobs` : `await JobRepository(session).list_filtered(status)` → router → repository (couche service sautée).
- `app/jobs/router.py:37` — `job_stats` : `await JobRepository(session).counts_by_status()` → idem.
- `app/jobs/router.py:46-52` — `retry_job` : instancie `JobRepository(session)`, appelle `repo.requeue(...)`, puis `AuditService(session).record(...)` et `await session.commit()` **dans le handler**. Le router porte la logique métier (relance), l'audit et la transaction.

**Correction concrète.** Étendre `JobService` (qui n'expose aujourd'hui que
`enqueue/claim/complete/fail`) avec les opérations admin : `list(status)`,
`counts_by_status()` et `retry(ctx, job_id)` — cette dernière regroupant
`requeue` + `AuditService.record` + `commit` dans **une seule transaction du service**.
Ajouter un provider `get_job_service(session=Depends(get_session))` et injecter
`svc: JobService = Depends(get_job_service)` dans les trois handlers, sur le modèle déjà
correct de `app/scoring/router.py:20` (`get_scoring_service`).

#### 2. `app/seed.py:37` — mot de passe admin par défaut en dur (secrets)

```python
ADMIN_PASSWORD = "ideaxion"  # à changer en prod via l'UI ou une variable d'env
```

Un identifiant admin faible et prévisible est codé en dur. Le commentaire renvoie la
responsabilité à l'exploitation, mais si le seed est rejoué en prod sans override, il
crée un compte administrateur au mot de passe public. Le principe « secrets chargés via
`app/core/config.py` (`SecretStr`), aucun secret en dur » n'est pas respecté pour ce cas.

**Correction concrète.** Charger le mot de passe de seed depuis `settings`
(`pydantic-settings` / `SecretStr`, ex. `SEED_ADMIN_PASSWORD`). En environnement prod,
refuser le démarrage/seed si la valeur est absente ou égale à la valeur par défaut
(fail-fast), et forcer un changement au premier login.

### 🟡 Mineur

#### 3. `app/instrumentation/router.py:24` — instanciation en ligne au lieu de l'injection

```python
return await AnalyticsService(InstrumentationRepository(session)).learning_dashboard()
```

Le handler construit lui-même le service et son repository au lieu de les recevoir via
`Depends`. La couche service est bien respectée (pas de fuite DB), mais le pattern est
incohérent avec le reste du code (`scoring/router.py` fournit un `get_scoring_service`).

**Correction.** Ajouter `get_analytics_service(session=Depends(get_session))` et injecter
`svc: AnalyticsService = Depends(get_analytics_service)`.

#### 4. `app/platform/router.py:27` — health check exécutant `text("SELECT 1")` dans le router

Le endpoint `/health` importe `sqlalchemy.text` et exécute une requête directement dans
le module router. C'est une **exception légitime** (sonde best-effort, bornée en temps,
sans valeur métier, ne devant jamais lever), mais elle contrevient à la lettre du
principe « le router ne touche jamais la DB ».

**Correction (optionnelle, pour la pureté).** Déplacer les sondes `_check_db/_check_redis/
_check_minio` dans un petit `HealthService` (ou `app/core`) et laisser le router se
contenter d'agréger les résultats.

#### 5. `app/core/storage.py` — I/O réseau MinIO sans retry / circuit breaker (principe 3)

Les opérations objet (`put_bytes`, `get_bytes`, `remove_object`, `stat_object`) appellent
le client MinIO sans les garde-fous appliqués au LLM (timeout applicatif, retry/backoff,
circuit breaker de `app/core/resilience.py`). Les URLs présignées sont générées localement
(pas d'I/O, sans risque), mais les get/put/remove sont des appels réseau best-effort non
protégés. Le principe « tout I/O externe est faillible » est pleinement tenu côté LLM,
partiellement côté storage.

**Correction légère.** Envelopper les opérations réseau du storage dans `with_retry`
(+ éventuellement un circuit breaker partagé), ou confirmer que tout up/download passe
par la file de jobs avec reprise — et documenter ce choix.

## Points conformes (à préserver)

- **Couche LLM — exemplaire.** `app/llm/openai_compatible.py` applique timeout par appel,
  `RetryPolicy` sur erreurs transitoires, circuit breaker par modèle et bascule dégradée
  (`app/llm/fallback.py`). Séparation nette erreurs transitoires / permanentes. Le
  provider Gemini est un stub qui `raise ConfigError` proprement (non câblé, rien à signaler).
- **Transitions de statut projet — conformes au modèle.** `ProjectService.transition_review`
  (`app/projects/service.py:53`) vérifie `can_transition_review(...)`, refuse via
  `BusinessRuleError`, enregistre l'audit (`old_value`/`new_value`) et `commit` **dans la
  même transaction**. Aucune écriture directe du statut hors service détectée.
- **RGPD.** `GdprService.delete_me` (`app/gdpr/service.py:96`) enregistre l'audit **avant**
  la suppression cascade, dans la même transaction ; l'audit survit à la purge.
- **Services sans SQL brut.** Aucun `text(...)` / `session.execute` dans les services
  métier (les correspondances initiales étaient des faux positifs).
- **Repositories sans HTTP.** Aucun repository n'importe `fastapi` ni ne connaît le HTTP.
- **Migrations réversibles.** Les 16 migrations Alembic possèdent toutes un `downgrade`
  non trivial.
- **Mailer borné.** `app/core/email.py` utilise `smtplib.SMTP(..., timeout=10)` en mode
  best-effort.
