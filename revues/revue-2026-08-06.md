## Constats détaillés

### Principe technique — Secrets / posture de sécurité (SEC)

#### 🟠 `app/sharing/models.py:34` + `app/sharing/service.py:48-56` — token de partage persisté en clair, en contradiction avec l'invariant documenté

Le modèle `ProjectShare` définit **deux** représentations du token :

```python
# app/sharing/models.py
token_hash: Mapped[str] = mapped_column(String(64), unique=True, index=True)
...
# Token brut pour affichage dans le dashboard porteur (risque faible : lecture publique, 90 j).
token: Mapped[str | None] = mapped_column(String(64), nullable=True, default=None)   # ← clair
```

et le service persiste bien les deux à la création :

```python
# app/sharing/service.py:48-56
token = secrets.token_urlsafe(24)
await self.repo.create(..., token=token, token_hash=_hash(token), ...)
```

> **Contradiction interne.** Le docstring du module (`sharing/models.py:4`) affirme :
> « Le token n'est jamais stocké en clair (hash). » Or `token` **est** stocké en clair.
> Un futur dev qui se fie à cet invariant construira dessus une hypothèse fausse.

> **Impact.** Le `token_hash` protège contre une fuite de base **uniquement si** le clair
> n'est pas conservé à côté. Ici, une lecture non autorisée de `project_shares` donne
> accès direct à **toutes les fiches partagées actives** (via `/shared/<token>`), y compris
> celles dont le porteur croit le lien « protégé ». Les tokens révoqués/expirés restent
> aussi en clair en base.

**Nuance de sévérité.** La fiche exposée est volontairement pauvre (score + synthèse +
forces, lecture jury/incubateur — jamais les internes du bilan) et le lien expire à 90 j
(SEC-11), d'où le « risque faible » assumé par le commentaire. Le classement 🟠 tient
surtout à la **contradiction avec l'invariant de sécurité affiché** : soit le module hashe
et ne garde pas le clair, soit il assume de tout garder en clair et corrige son docstring —
l'état intermédiaire actuel est le pire des deux (fausse impression de protection).

**Correction concrète.** Deux options cohérentes, au choix :
1. **Ne pas persister le clair.** Supprimer la colonne `token` (migration Alembic
   réversible). Pour le ré-affichage du lien dans le dashboard porteur, soit retourner le
   token **une seule fois** à la création (déjà fait via `ShareOut.token`), soit générer un
   lien signé côté serveur à la demande. `list_my_shares` (`service.py:73`) n'exposerait
   plus l'URL complète mais un statut + un bouton « recréer le lien ».
2. **Assumer explicitement le clair** (si l'UX « revoir mon lien » est jugée indispensable) :
   corriger le docstring `models.py:4` pour refléter la réalité, et **restreindre** l'accès
   à cette colonne (jamais dans un DTO exposé au-delà du propriétaire, ce qui est le cas
   aujourd'hui — bon point). Documenter la décision comme un compromis SEC assumé.

L'option 1 est alignée avec le reste du code base, qui hashe systématiquement ses secrets
sans en garder le clair (`iam/invitations`, `mentors` token d'invitation, `academy` share).

## Points conformes (rotation du jour)

- **Pipeline diagnostic — exemplaire (Principes 3, 4 et file de jobs).**
  `app/diagnostics/handlers.py` (`handle_run_diagnostic`) est un modèle de traitement lourd
  et faillible sorti de la requête HTTP :
  - **Phasage résilient.** Phase 1 (Radar) commité seul → le porteur voit son score sans
    attendre le rapport LLM ni le PDF. Phase 2 (rapport + PDF) est **best-effort** : chaque
    étape faillible est encapsulée (`try/except` + `logger.warning`), une panne
    LLM/WeasyPrint/MinIO ne casse jamais le bilan.
  - **Tolérance aux passes.** Les 3 passes de scoring tournent en parallèle
    (`asyncio.gather(..., return_exceptions=True)`) ; le consensus se construit même avec
    moins de 3 passes réussies, et ne lève **que si toutes** échouent (confiance moindre
    signalée). CPU-bound et I/O bloquant déportés hors event loop (`asyncio.to_thread` pour
    le rendu PDF et le `put_bytes` MinIO).
  - **Reprise d'échec.** `handle_run_diagnostic_failed` sort le bilan de l'attente infinie
    (`pending → failed`), avec un cas subtil bien traité : si la Phase 1 a réussi
    (`radar_score` présent) mais la Phase 2 a échoué définitivement, le bilan bascule en
    **Radar-only READY** plutôt qu'en échec dur — le score déjà calculé n'est pas perdu.
    Commit du statut **isolé** de la notification (best-effort) pour qu'une notif défaillante
    ne masque jamais le correctif.
  - **Traçabilité.** `diagnostic.scored` audité dans la transaction de la Phase 1
    (`overall`, `confidence`, `needs_review`).
- **Diagnostic — couches propres.** `diagnostics/router.py` : DI via
  `Depends(get_diagnostic_service)`, garde de taille par chunks (SEC-04, refus 413 avant
  chargement mémoire), rate-limit `fail_open=False` sur les endpoints coûteux (anti-abus
  coût LLM), vérif de propriété du document (SEC-07) côté service. `diagnostics/service.py`
  crée projet + diagnostic + bilan `pending` + audit + `enqueue` **en une seule transaction
  atomique**. Aucune fuite HTTP dans `diagnostics/repository.py`.
- **`AuditService` — pattern transactionnel juste.** `audit/service.py:record` n'ouvre ni ne
  commite de transaction : il `add` + `flush` dans la session de l'appelant. L'audit est donc
  persisté **atomiquement avec l'action, ou pas du tout** — exactement le principe 4.
- **Machine à états.** Le handler diagnostic passe les statuts par le repository
  (`projects.set_diagnostic_status`, `projects.set_review_status`) et non par écriture
  directe sur le modèle — conforme (contraste avec le point ouvert `pitchsim/service.py:605`).
- **Migrations réversibles.** Les 16 révisions Alembic ont **toutes** un `downgrade`.
- **Webhooks.** `app/_v2/` n'est pas présent/monté (`app/main.py` ne monte qu'`api_router`) —
  rien à signaler sur l'idempotence des webhooks tant que le MVP ne les câble pas.
