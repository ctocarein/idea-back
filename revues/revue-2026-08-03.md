## Constats détaillés

### Principe 2 — Séparation en couches (`router → service → repository → DB`)

#### 🟠 `app/jobs/router.py:46-52` — le router orchestre repo + audit + commit
Le handler `retry_job` instancie `JobRepository(session)` et `AuditService(session)` **en ligne**, puis enchaîne `repo.requeue(job)` + `AuditService.record(...)` + `await session.commit()` directement dans le router.

> Principe violé : « la transaction et l'audit appartiennent au service, jamais au router ». Une relance de job est une action sensible (elle doit être auditée dans la même transaction).

**Correction :** créer `app/jobs/service.py` avec une méthode `requeue_job(actor_id, job_id)` qui porte get → requeue → audit → commit, injectée via `Depends(get_job_service)`. Le router ne fait plus qu'appeler le service.

#### 🟠 `app/scoring/governance.py:49-61` — même schéma sur l'activation de grille
`activate_grid` instancie `ScoringRepository(session)` en ligne, appelle `repo.activate(grid)` + `AuditService.record(...)` + `await session.commit()` dans le handler. Activer une grille Radar = **changement de configuration sensible** ; il doit passer par une couche métier.

**Correction :** déplacer la logique dans `ScoringService.activate_grid(actor_id, version)` (transaction + audit côté service) ; injecter via une dépendance. `list_grids:39` fait aussi `ScoringRepository(session)` inline (lecture — moindre, à uniformiser en même temps).

Contre-exemple conforme dans le même module : `app/scoring/router.py:20` définit `get_scoring_service(...)` et le handler délègue proprement au service. C'est le pattern à généraliser.

#### 🟡 Instanciation en ligne en lecture seule
`app/jobs/router.py:28,37` (`JobRepository(session).list_filtered / counts_by_status`) et `app/instrumentation/router.py:24` (`AnalyticsService(InstrumentationRepository(session))`) assemblent le repo/service dans le handler au lieu d'une dépendance `Depends(get_*_service)`. Lecture seule, pas de mutation — mais incohérent avec le pattern DI du reste du code. Extraire un `dependencies.py` par feature.

### Principe 3 — Tout I/O externe est faillible

#### 🟠 `app/core/storage.py` — MinIO sans timeout / retry / circuit breaker
Les opérations réseau MinIO (`put_object`, `get_object`, `stat_object`, `remove_object`, `list_buckets`) ne sont **pas** enveloppées par `app/core/resilience.py`, contrairement aux providers LLM. La dégradation gracieuse ne couvre que le cas « non configuré » (`get_storage()` renvoie `None`), **pas** le cas « configuré mais down/lent » : un MinIO injoignable peut bloquer un job worker (appelé via `asyncio.to_thread`) jusqu'au timeout par défaut d'urllib3.

> L'archi prévoit explicitement « MinIO 15 s » de timeout + retry + circuit breaker (§12.3).

**Correction :** borner le timeout du client `Minio` (via `http_client=urllib3.PoolManager(timeout=...)`, ≈15 s) et envelopper les appels dans `with_retry` + `CircuitBreaker` comme le fait `app/llm/openai_compatible.py`.

## Points conformes

- **Résilience LLM (exemplaire).** `app/llm/openai_compatible.py` : timeout par appel (`httpx.Timeout`), `RetryPolicy(max_attempts=3, retry_on=TransientLLMError)`, `CircuitBreaker` par modèle. DeepSeek / Mistral / OpenAI héritent tous du provider commun → garde-fous appliqués partout. Modèle de référence pour le principe 3.
- **Mailer.** `app/core/email.py` : timeout présent.
- **Secrets (Principe config).** `app/core/config.py` : `BaseSettings` + `SecretStr` ; aucun secret en dur détecté sur les 189 fichiers ; MinIO dégrade proprement si les clés sont absentes.
- **Audit transactionnel (Principe 4).** `AuditService.record` appelé sur les actions sensibles : suppression RGPD (`app/gdpr/service.py`), grants IAM, mentors (9 sites), projets, reports, diagnostics — dans la même transaction que l'action.
- **Machine à états (Principe 8).** Aucune écriture directe de statut hors couche. `app/projects/service.py:transition_review` passe par le guard `can_transition_review(...)` + audit + commit, dans le service. `ProjectService`/`models.py` portent `can_transition`.
- **Migrations réversibles.** 16 révisions Alembic, **toutes** avec `upgrade` ET `downgrade` non triviaux.
- **Webhooks / `_v2`.** `app/_v2/` non présent/non monté en MVP → rien à signaler (conforme au périmètre §17).
- **Health check.** `app/platform/router.py` utilise `text("SELECT 1")` dans le router : sonde de liveness best-effort, bornée en temps, sans données métier → exception acceptable, pas une violation de couche.
