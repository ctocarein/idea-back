## Constats détaillés

### Principe 1 — Séparation en couches

**🟠 IMPORTANT — `app/jobs/router.py:40-53` (`retry_job`) : le router orchestre repo + audit + transaction.**
Le handler instancie `JobRepository(session)` en ligne, appelle `repo.get_by_id()` puis `repo.requeue()`, `AuditService(session).record(...)` **et** `session.commit()` — le tout dans le router. Le référentiel est explicite : *« la transaction et l'audit appartiennent au service, jamais au router »*. Un `JobService` existe déjà (`app/jobs/service.py`) mais n'expose pas de méthode `retry`.
Accessoirement, `list_jobs` (l.28) et `job_stats` (l.37) appellent `JobRepository(session)` directement → la couche service est sautée.
**Correction :** ajouter `JobService.retry(job_id, actor_id)` (get + requeue + audit + commit atomiques) et `JobService.list/stats`, puis injecter via `Depends(get_job_service)` ; le router ne fait plus qu'appeler le service.

**🟠 IMPORTANT — `app/diagnostics/handlers.py:152,155,228,283` : écriture directe du statut projet via le repository, sans garde de machine à états.**
Les handlers du pipeline diagnostic écrivent `diagnostic_status` / `review_status` par `projects.set_diagnostic_status(...)` / `set_review_status(...)` (méthodes du **repository** projet), depuis un autre module. Le référentiel demande que toute transition de statut passe par un service projet gardé, *« jamais d'écriture directe du statut depuis un autre module ni via le repository »*. Surtout, la garde `can_transition_diagnostic` (`app/projects/models.py:85`) est **définie mais jamais appelée** → les transitions du statut diagnostic ne sont pas gardées (sauts illégaux possibles). L'audit, lui, est bien présent (`diagnostic.scored`).
**Correction :** exposer `ProjectService.change_diagnostic_status(project, target)` appliquant `can_transition_diagnostic`, et l'appeler depuis les handlers au lieu du repository. (À noter : l'axe `review_status` a déjà son service gardé — voir points conformes — l'axe diagnostic ne l'a pas.)

**🟡 MINEUR — `app/instrumentation/router.py:24` : instanciation en ligne dans le handler.**
`AnalyticsService(InstrumentationRepository(session))` est construit à la main dans le handler au lieu d'être injecté via `Depends(get_analytics_service)`. Cohérence d'injection (cf. `app/scoring/router.py` qui, lui, fait bien une fabrique `get_scoring_service`).

**🟡 MINEUR — `app/platform/router.py:27` : `text("SELECT 1")` exécuté dans le router.**
Sonde de liveness (`_check_db`). Exception pragmatique acceptable (un health check qui vérifie la connectivité DB ne passe pas par un repository), mais c'est techniquement un router qui touche la DB — à documenter comme exception assumée.

### Principe 3 — Tout I/O externe est faillible

**🟠 IMPORTANT — `app/core/storage.py:87` : client MinIO sans timeout / retry / circuit breaker.**
`Minio(...)` est instancié sans `http_client` ni timeout explicite ; les opérations (`put_object`, `get_object`, `presigned_*`, `stat_object`, `remove_object`) n'ont ni timeout, ni retry, ni circuit breaker — contrairement à la couche LLM qui est exemplairement enveloppée. Un MinIO lent/injoignable peut faire pendre un job. Mitigation partielle : dégradation gracieuse assumée (PDF optionnel, bilan `ready` sans PDF).
**Correction :** envelopper les appels storage avec timeout + `CircuitBreaker` / `with_retry` (`app/core/resilience.py`, comme `app/llm/openai_compatible.py`), ou a minima `Minio(http_client=urllib3.PoolManager(timeout=...))`.

**🟡 MINEUR — `app/core/email.py:33` : SMTP best-effort avec timeout mais sans retry ni circuit breaker.**
`smtplib.SMTP(..., timeout=10)`, ne lève jamais, logge en cas d'échec. Acceptable en mode dégradé best-effort ; à durcir (retry/back-off ou passage par la file de jobs) si l'email devient critique (vérification de compte, invitations).
