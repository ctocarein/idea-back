## Constats détaillés

### Principe 6 — Tout est traçable

#### 🟠 `app/iam/oauth_service.py:94-99` — échec d'appel externe OAuth avalé sans log structuré

```python
try:
    identity = await fetch_identity(
        provider, code=code, redirect_uri=self._backend_callback(provider)
    )
except Exception:
    return self._front_error(front_redirect, "oauth_failed")
```

`fetch_identity` (`app/iam/oauth_providers.py:88`) réalise **deux appels réseau sortants** vers le
fournisseur (échange du `code` contre un jeton, puis lecture du `userinfo`). Toute erreur — panne
fournisseur, quota, réponse JSON illisible, `access_token` absent, `raise_for_status` — est
capturée par un `except Exception` **muet** : aucun `logger.warning/error`. `app/iam/router.py`
n'instancie d'ailleurs aucun logger.

> **Principe violé :** « appel externe → log structuré » (Principe 6). C'est aussi la seule
> famille d'erreurs de tout le flux qui ne produit **aucune** trace observable côté serveur.

**Impact.** En production, une coupure ou une régression de configuration OAuth (mauvais
`client_secret`, `redirect_uri` non déclaré côté Google, etc.) se traduit uniquement par des
utilisateurs redirigés vers `login?error=oauth_failed`, **sans aucun signal côté backend** pour
corréler, alerter ou mesurer le taux d'échec. Le chemin `_resolve_account → ("error", None)`
(email fournisseur absent, `oauth_service.py:135`) est lui aussi silencieux.

**Correction concrète.** Ajouter un logger structuré au module (`logger = get_logger("oauth")`,
cf. `app/inconsistencies/service.py:37`) et tracer l'échec avant le repli, en gardant le contexte
utile mais **sans** le `code` ni le `client_secret` :

```python
except Exception as exc:
    logger.warning("oauth_provider_failed", provider=provider,
                   error=f"{type(exc).__name__}: {exc}")
    return self._front_error(front_redirect, "oauth_failed")
```

Idem sur le retour `("error", None)` de `_resolve_account` (`oauth_no_email`, provider).

### Principe 3 — Tout I/O externe est faillible

#### 🟡 `app/iam/oauth_providers.py:95-117` — appel fournisseur avec timeout mais sans retry / circuit breaker

`fetch_identity` ouvre un `httpx.AsyncClient(timeout=15.0)` — le **timeout est présent** (bon
point), mais l'appel n'a **ni retry/backoff ni circuit breaker** via `app/core/resilience.py`,
contrairement à ce que le Principe 3 pose comme invariant pour tout I/O externe (pleinement tenu
côté LLM). Une micro-coupure transitoire du fournisseur fait échouer le login au lieu de retenter,
et un fournisseur lent immobilise la requête jusqu'à 15 s.

**Nuance de sévérité.** Il s'agit d'un flux **interactif** (login), pas d'un traitement de fond :
la dégradation est gracieuse (redirection `?error=`) et l'utilisateur peut relancer. Le classement
🟡 est cohérent avec le traitement actuel du mailer (`app/core/email.py`, timeout seul,
best-effort) et du storage MinIO (point structurel déjà ouvert).

**Correction légère.** Envelopper l'échange de jeton dans `with_retry` (retries bornés sur erreurs
transitoires 5xx / réseau uniquement, **jamais** sur un 4xx du fournisseur), et documenter le
choix si l'on préfère volontairement ne pas retenter un flux interactif.

## Points conformes (modules neufs de la fusion)

- **`app/sharing` — invariant token corrigé.** Le token de partage n'est plus persisté en clair
  (`models.py` ne garde que `token_hash` ; `service.py:48` ne stocke que le hash et retourne le
  clair une seule fois). Résout le 🟠 tête de la revue 2026-08-06.
- **OAuth — conception sécurisée (Principes conservés).** `app/iam/oauth_service.py` :
  `state` opaque **à usage unique** en Redis (anti-CSRF, `getdel`), **code intermédiaire à usage
  unique** (le jeton ne transite jamais dans l'URL front), **garde anti open-redirect**
  (`_assert_allowed_redirect` restreint le `redirect_uri` aux origines CORS de confiance),
  **liaison automatique de compte uniquement si `email_verified` ET compte `ACTIVE`** (sinon
  conflit 409 → pas de détournement), secrets `client_secret` chargés en **`SecretStr`** via
  `app/core/config.py`, et **audit `auth.oauth_registered`** dans la transaction de création.
- **`ProjectStateService` — machine à états exemplaire (Principes 2 & 6).**
  `app/projects/state_service.py` : `transition_diagnostic` / `transition_review` vérifient
  `can_transition_*`, refusent via `BusinessRuleError`, passent le statut **par le repository**
  (jamais d'écriture directe sur le modèle) et enregistrent l'audit (`old_value`/`new_value`)
  **dans la transaction appelante**. Contraste net avec le point ouvert `pitchsim/service.py:605`.
- **Espace porteur — couches propres.** `app/projects/owner_router.py` : DI systématique via
  `Depends(get_*_service)`, `response_model` partout, aucun SQL ni audit/commit dans les handlers.
  `owner_service.py` et `evaluation_service.py` gardent la propriété via `guard_owner_access`,
  et aucun repository neuf (`project_memory`, `projects`) n'importe `fastapi`/HTTP.
- **Détecteur d'incohérences — résilience exemplaire (Principe 3).** `app/inconsistencies/service.py`
  est un **outil batch offline** (aucun `router.py`, non monté dans `app/main.py`) : chaque passe
  LLM est encapsulée (`_ask` : `try/except` → dégradation `None` + `logger.warning`), la concurrence
  est **bornée par sémaphore**, un dossier en échec est rapporté **sans jamais interrompre le lot**
  (double filet `analyze_batch`), et tout est tracé en logs structurés avec **version de prompt**
  (`INCONSISTENCY_PROMPT_VERSION`). La résilience de l'appel LLM (timeout/retry/circuit breaker)
  est fournie par la couche `app/llm`.
