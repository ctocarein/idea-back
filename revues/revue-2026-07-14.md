## Constats détaillés (nouveaux)

### Principe 1 — Séparation en couches (`router → service → repository`)

**🟡 Mineur — `app/instrumentation/router.py:24` — service instancié en ligne dans le handler.**
La route `learning_dashboard` construit sa dépendance à la main :
```python
return await AnalyticsService(InstrumentationRepository(session)).learning_dashboard()
```
au lieu de passer par une fabrique injectée `Depends(get_analytics_service)`. Même classe d'écart que `jobs/router.py` (déjà connu), mais **non signalée jusqu'ici** pour ce module. Route en **lecture seule** (dashboard admin, `AUDIT_READ`), sans transaction ni audit — impact faible, mais convention DI non respectée.
*Correction :* ajouter dans le module une fabrique `def get_analytics_service(session=Depends(get_session)) -> AnalyticsService: return AnalyticsService(InstrumentationRepository(session))` et l'injecter via `svc: AnalyticsService = Depends(get_analytics_service)`, comme le fait proprement `scoring/router.py:20` (`get_scoring_service`).

**🟡 Mineur — `app/projects/router.py:74-77` — router appelant directement un repository.**
La route `project_timeline` court-circuite le service :
```python
audit: AuditRepository = Depends(get_audit_repo),
...
rows = await audit.list_for_entity("project", project_id)
```
Le flux `router → service → repository` veut que la lecture passe par un service (ex. `ProjectAdminService` ou un `AuditService.timeline(...)`). Ici le router parle au repository. C'est une **lecture pure** (journal d'audit, aucune mutation) avec DI correcte (`Depends(get_audit_repo)`), donc à faible risque — mais c'est un saut de couche à corriger pour rester homogène.
*Correction :* exposer `ProjectAdminService.timeline(ctx, project_id)` (ou `AuditService.list_for_entity`) et faire appeler le service par le router.
