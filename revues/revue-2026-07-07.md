## Constats détaillés (commit 24 h)

### Principe 3 — robustesse I/O LLM · plafond de sortie incohérent entre voie texte et voie vision

🟡 **`app/llm/base.py:28-34` + `app/llm/openai_compatible.py:115-134` + `app/llm/fallback.py:47-54`** — le commit ajoute un override `max_tokens` au **protocole `analyze_json`** et le propage (OpenAI-compat, fallback, mock, gemini), puis l'utilise pour relever le plafond de l'extraction à 3072. **Mais la méthode sœur `analyze_json_with_images` n'a PAS reçu ce paramètre** : dans `openai_compatible.py`, elle appelle `_chat(messages, json_mode=True, model=self.vision_model)` **sans `max_tokens`** → sortie toujours plafonnée à `self._max_tokens` (défaut 1024). Or c'est exactement le comité `app/pitchsim/service.py:595-596` (JSON multi-critères sur slides) qui l'utilise : **même risque de JSON tronqué → `LLMParseError` → 500** que celui corrigé aujourd'hui pour le texte. La correction ferme la fuite d'un côté mais laisse l'autre ouvert.
*Correction suggérée :* étendre la signature `analyze_json_with_images(..., max_tokens: int | None = None)` (protocole + OpenAI-compat + fallback) et faire suivre `_chat(..., max_tokens=max_tokens)` ; côté `pitchsim`, passer un plafond adapté à la sortie du comité. Sur la voie de repli texte (`return await self.analyze_json(prompt, schema=schema)`), propager aussi le `max_tokens`.

### Principe 3 — plombage `max_tokens or self._max_tokens` (falsy)

🟡 **`app/llm/openai_compatible.py:62`** — `"max_tokens": max_tokens or self._max_tokens`. Le `or` retombe sur le défaut pour **toute** valeur falsy, y compris `0`. Sans conséquence aujourd'hui (les appelants passent `None` ou `3072`), mais l'idiome robuste est explicite. Cosmétique.
*Correction suggérée :* `max_tokens if max_tokens is not None else self._max_tokens` (cohérent avec la sémantique « None → défaut du provider » documentée dans `base.py`).
