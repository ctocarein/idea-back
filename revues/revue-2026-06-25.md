## Constats détaillés

### Principe 1 & 2 — Séparation en couches / `core` technique vs feature métier

#### 🟠-2 · Logique de service + transaction orchestrées dans le router (2 endroits)

Deux routers d'administration court-circuitent la couche service : ils instancient directement le repository, appellent l'audit et committent la transaction depuis le handler HTTP. Il n'existe pas de `JobService` ni de service dédié à la gouvernance de grille.

- `app/jobs/router.py:44-52` — le handler `retry` fait `JobRepository(session)` + `AuditService(session).record(...)` + `await session.commit()` directement.
- `app/scoring/governance.py:37-61` — le handler d'activation de grille fait `ScoringRepository(session)` + `AuditService(...).record(...)` + `await session.commit()` directement.

*Principe violé :* §4 « le `router` ne touche jamais la DB ; il traduit HTTP ↔ appel service ». L'orchestration (écriture + audit + commit) appartient à la couche service.
*Correction :* extraire un `JobService.retry(ctx, job_id)` et un `ScoringGovernanceService.activate(ctx, grid_id)` portant la transaction ; le router se limite à `Depends(get_..._service)` puis à l'appel. (La traçabilité, elle, est correcte : audit et écriture partagent bien le même `commit`.)

#### 🟡-1 · SQL brut dans le router de healthcheck

`app/platform/router.py:27` exécute `await session.execute(text("SELECT 1"))` directement dans le handler HTTP.
*Principe violé :* §3 « si un fichier importe `sqlalchemy`/la session, c'est un repository ; s'il fait les deux, c'est un bug de couche ». Tolérable pour un *liveness probe*, mais à déplacer dans un `health_check()` côté `core/database` ou un repo dédié pour rester cohérent.

#### 🟡-2 · Câblage de dépendance en ligne dans le handler

`app/instrumentation/router.py:24` assemble `AnalyticsService(InstrumentationRepository(session))` à l'intérieur du handler au lieu de passer par une factory `Depends` (cf. le modèle `get_project_service` de §4.2). Lecture seule, faible impact, mais incohérent avec le reste du code.

> **Non-constats vérifiés :** les `dependencies.py` qui importent à la fois `fastapi` et `sqlalchemy` (iam, projects, diagnostics, mentors, etc.) sont **conformes** — c'est exactement le patron d'injection documenté en §4.2. Les repositories ne connaissent pas le HTTP (aucune fuite de `Request`/`HTTPException`). `scoring/router.py` n'utilise la session que dans une factory.

### Principe 3 — Tout I/O externe est faillible

#### 🟠-3 · Stockage MinIO sans timeout / retry / circuit breaker applicatif

`app/core/storage.py` — les appels réseau bloquants (`put_bytes`/`put_object`, `ensure_bucket`, `health_ok`, `list_buckets`) n'ont **pas** de timeout configuré côté app, ni de retry, ni de circuit breaker. Seul le **mode dégradé** est présent (les appelants enveloppent dans `try/except` → bilan `ready` sans PDF : `diagnostics/handlers.py:158-176`).
*Principe violé :* §1.5 / §12.3 — « chaque appel sortant a un timeout, une stratégie de retry, un circuit breaker **et** un mode dégradé. Invariant, pas option. » La couche LLM respecte les quatre ; le stockage n'en a qu'un.
*Correction :* envelopper les opérations MinIO bloquantes via `app/core/resilience` (`with_retry` + `CircuitBreaker`) et fixer un timeout client explicite (l'archi cible 15 s pour MinIO), comme le fait déjà `app/llm/openai_compatible.py:80`.

> **Point fort (voir « Points conformes ») :** la couche `app/llm` est une implémentation **modèle** de ce principe.

### Machine à états & transitions de statut

#### 🟠-1 · Garde-fou de transition diagnostic défini mais jamais appelé *(le plus urgent)*

`app/projects/models.py:85` définit `can_transition_diagnostic(...)` et `DIAGNOSTIC_TRANSITIONS` (lignes 57-66), mais **aucun appelant** dans tout le code (`rg can_transition_diagnostic` → 1 seule occurrence, la définition). Le statut est écrit en direct :

- `app/diagnostics/service.py:101` — création directe en `DIAGNOSTIC_IN_PROGRESS` ;
- `app/diagnostics/handlers.py:169-170` — `set_diagnostic_status(COMPLETED)` puis `set_diagnostic_status(BILAN_READY)` enchaînés sans validation.

*Principe violé :* §8 « aucune transition implicite, tout saut illégal → 422 ». Le moteur de transition existe mais est contourné — c'est du code de garde **mort**.
*Correction :* faire passer toute écriture de `diagnostic_status` par une méthode gardée (ex. `ProjectService.advance_diagnostic(project, target)` qui appelle `can_transition_diagnostic` et lève `BusinessRuleError` sinon), à l'image de `transition_review` qui, lui, utilise bien `can_transition_review`.

#### 🟡-3 · Auto-routage worker contournant `can_transition_review`

`app/diagnostics/handlers.py:174` appelle `projects.set_review_status(project, IN_REVIEW)` en direct. Le chemin admin (`projects/service.py:54-60`) valide pourtant via `can_transition_review` ; le chemin worker, lui, écrit sans garde. Même remède que 🟠-1 : centraliser derrière une transition gardée.
