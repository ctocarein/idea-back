## Constats détaillés

### Principe 1 — Séparation en couches (`router → service → repository → DB`)

**🟠 Important — Transitions de statut diagnostic hors service et hors garde de machine à états**
`app/diagnostics/handlers.py:169-174`
Le handler `run_diagnostic` appelle directement
`projects.set_diagnostic_status(project, DIAGNOSTIC_COMPLETED)`, puis `BILAN_READY`, puis
`set_review_status(...)` sur le **repository**. Or l'architecture (§8) impose : « Les
modules qui déclenchent une transition n'écrivent jamais le statut directement : ils
appellent `ProjectService.change_status(...)` ». De plus, le garde
`can_transition_diagnostic` (défini dans `app/projects/models.py:85`) **n'est jamais
appelé** : aucune transition diagnostic ne vérifie sa légalité, contrairement à la
curation (`transition_review`, qui appelle bien `can_transition_review`).
*Correction :* exposer `ProjectService.change_diagnostic_status(...)` qui applique le
garde + l'audit dans une transaction, et l'appeler depuis le handler. Cela réutilise le
garde mort et aligne le pipeline diagnostic sur le pattern de la curation.

**🟠 Important — Le router orchestre repo + audit + commit (logique métier dans la couche HTTP)**
`app/jobs/router.py:48-53` et `app/scoring/governance.py:53-61`
Les deux handlers font, **dans le router** : `repo.requeue(job)` / `repo.activate(grid)`,
puis `AuditService(session).record(...)`, puis `await session.commit()`. La garantie
transaction + audit doit vivre dans un service (§4.3 : « C'est le service qui porte cette
garantie, jamais le router »). Ici le router décide de la transaction et de l'audit — il
sort de son rôle de simple traducteur HTTP.
*Correction :* déplacer la logique dans `JobService.retry()` et un
`ScoringService.activate_grid()` ; le router se contente d'appeler le service.

**🟡 Mineur — SQL brut dans le router de health-check**
`app/platform/router.py:27` — `await session.execute(text("SELECT 1"))` directement dans
le handler `/health`. Tolérable pour un ping de liveness, mais idéalement délégué à un
`HealthService`/repository pour rester cohérent avec la règle « le router ne touche jamais
la DB ».

**🟡 Mineur — Instanciation inline des repos/services au lieu de l'injection `Depends`**
`app/instrumentation/router.py:23`, `app/jobs/router.py`, `app/scoring/governance.py`,
`app/scoring/router.py` instancient `Repository(session)` / `Service(...)` à la main dans
le handler. L'architecture (§4.2) prescrit l'injection via `dependencies.py`
(`Depends(get_*_service)`) pour la testabilité. Incohérence de style — certains modules
respectent le pattern (`projects`), d'autres non.

### Principe 2 — `core` technique / features métier

### Principe 3 — Tout I/O externe est faillible

**🟠 Important — Appels MinIO sans timeout / retry / circuit breaker**
`app/core/storage.py:27-55` (`put_bytes`, `presigned_*`, `remove_object`)
Le chemin LLM est exemplaire (cf. points conformes), mais le stockage objet appelle le
client `minio` en direct, **sans** timeout explicite, retry ni circuit breaker — alors que
l'archi §12.3 impose un timeout MinIO de 15 s. La dégradation gracieuse existe côté
appelant (`handlers.py:154` : « bilan `ready` sans PDF » sur exception), ce qui limite
l'impact, mais le garde-fou I/O lui-même manque (principe 3 : « invariant, pas option »).
*Correction :* configurer le timeout du client MinIO et envelopper les opérations réseau
dans `with_retry` + `CircuitBreaker` (réutiliser le pattern de
`app/llm/openai_compatible.py`).

**🟡 Mineur — Provider Gemini en stub qui lève à l'instanciation**
`app/llm/gemini.py` lève `ConfigError` dès `__init__`. Sans danger tant que
`LLM_PROVIDER != gemini`, mais la `factory` peut le retourner si la config le demande →
crash au démarrage seulement. À garder en tête lors de la mise en prod (DeepSeek/Mistral
couvrent le MVP).
