## Constats détaillés (nouveaux)

### Principe 3 & 4 — Tout I/O externe est faillible / traitement bloquant hors requête HTTP

**🟠 Important — `app/documents/service.py:62,66,69,88` : appels MinIO synchrones bloquants dans un handler `async`, sans timeout.**

`app/core/storage.py` est **entièrement synchrone** (0 `async def` ; `put_bytes`, `get_bytes`,
`stat_object`, `remove_object` sont des méthodes bloquantes qui font du réseau vers MinIO). Or
`DocumentService` les appelle **directement dans des méthodes `async`** exécutées dans la requête
HTTP :

- `confirm_upload` → `self.storage.stat_object(doc.object_key)` (l.62), puis
  `self.storage.remove_object(...)` (l.66, l.69) ;
- `delete` → `self.storage.remove_object(doc.object_key)` (l.88).

Deux violations cumulées :

1. **Blocage de l'event loop (principe 4).** Un appel réseau **synchrone** dans un handler `async`
   **gèle la boucle d'événements** pour toute sa durée : aucune autre requête n'est servie pendant
   l'aller-retour MinIO. C'est exactement l'anti-pattern relevé le 07-02 pour le PDF pitchsim. Le
   contre-exemple exemplaire est dans le même codebase :
   `app/diagnostics/handlers.py:149` fait `await asyncio.to_thread(render_bilan_pdf, ...)` pour
   déporter le travail bloquant hors de la boucle.
2. **Aucun garde-fou de faillibilité (principe 3).** `storage.py` n'a ni timeout, ni retry, ni
   circuit breaker (`app/core/resilience.py` non utilisé — constat persistant). Un MinIO lent ou
   injoignable ne se contente donc pas d'échouer proprement : il **suspend le worker** le temps du
   timeout TCP par défaut.

*Correction :*
- À court terme, envelopper chaque appel storage bloquant dans
  `await asyncio.to_thread(self.storage.stat_object, doc.object_key)` (idem `remove_object`) pour
  libérer l'event loop.
- À moyen terme, faire porter à `app/core/storage.py` les garde-fous `resilience.py` (timeout court
  + retry + circuit breaker), au même titre que `app/llm`. Cela résout d'un coup ce constat **et**
  le constat persistant `storage`.

### Principe 6 — Tout est traçable

**🟡 Mineur — `app/documents/service.py:80-92` : la suppression d'un document n'est pas auditée.**

`DocumentService.delete` retire l'objet MinIO puis supprime la ligne (`repo.delete` + `commit`)
**sans `AuditService.record(...)`** — `DocumentService` ne reçoit d'ailleurs pas d'`auditor`
(`__init__`, l.25). Supprimer un document d'un porteur (pièce de la data room / du diagnostic) est
une action sensible qui devrait laisser une trace, au même titre que l'effacement RGPD voisin
(`gdpr/service.py:96`, lui audité). C'est le **même angle mort** que `opportunities`/`sharing`
(constats persistants).

*Correction :* injecter `AuditService` dans `DocumentService` et tracer, avant `commit()` :
`action="document.deleted", entity="document", entity_id=document_id`.

**🟡 Mineur — `app/gdpr/service.py:40-87` : l'export de portabilité n'est pas tracé.**

`GdprService.delete_me` audite bien l'effacement (l.96), mais `GdprService.export` — qui **extrait
l'intégralité des données personnelles** du porteur (compte, projets, bilans, documents) — ne
produit **aucune trace**. Un accès complet aux données personnelles est un événement RGPD à
journaliser (qui a exporté quoi, quand). Impact limité (lecture seule, périmètre = soi-même), d'où
🟡.

*Correction :* `await self.auditor.record(actor_id=u.id, action="user.exported", entity="user",
entity_id=u.id)` puis `commit()` en fin d'`export` (l'auditor est déjà injecté dans le service).

### Principe 4 — Traitement LLM hors requête HTTP

**🟡 Mineur — `app/academy/service.py:81` : appel LLM synchrone dans la requête HTTP (« construire guidé »).**

`guided_turn` fait `result = await self.provider.complete(prompt)` **dans le handler HTTP**
(`POST /academy/build/{session_id}/turn`). La lettre du principe 4 est « toute analyse LLM passe par
la file de jobs, jamais dans la requête HTTP ». Ici la contrainte est **atténuée** : il s'agit d'un
coach **conversationnel tour-par-tour**, où une réponse synchrone est inhérente à l'UX (un job
asynchrone casserait l'interaction). De plus l'appel passe par `app/llm`, dont la résilience est
**confirmée conforme** (timeout `settings.llm_timeout_seconds`, `RetryPolicy`, `CircuitBreaker`,
fallback — `app/llm/openai_compatible.py:32,45,48`). Ce n'est donc pas une faille, mais un point de
**latence de queue** : chaque tour occupe une connexion le temps de l'inférence.

*Recommandation :* documenter ce choix comme exception assumée au principe 4 (chat interactif), et
s'assurer que le timeout LLM par appel reste **serré** (quelques secondes) pour qu'un modèle bloqué
ne retienne pas la connexion. Aucune action code impérative au stade MVP.

## Points conformes (à préserver)

- **`app/gdpr/service.py` — droit à l'oubli exemplaire.** `delete_me` **audite AVANT la cascade**
  (`auditor.record(action="user.deleted")`, l.96), dans la **même transaction** que
  `session.delete(user)` + `commit()` (l.97-98), avec nettoyage MinIO **best-effort après** le
  commit (l.99-104) et commentaire explicite sur la survie de la trace (`actor_id` non contraint
  par FK). Modèle à suivre pour toute action destructive.
- **`app/documents` — presigned solide.** L'API **ne transporte jamais les octets** (URL PUT signée,
  l.49), garde propriétaire `guard_owner_access` sur `confirm`/`delete` (l.57,84), et **validation
  post-upload SEC-06** (taille + content-type re-vérifiés côté serveur via `stat_object`, l.62-70,
  avec suppression de l'objet si non conforme). Couches nettes, `commit` porté par le service.
- **`app/academy` — gardes et frontières produit respectées.** `guard_owner_access` sur chaque
  session guidée (`_load_owned_session`, l.75), vérification d'appartenance projet **SEC-07**
  (l.63-66), complétion de leçon **idempotente** (l.49), gates de permission `require(Permission.*)`
  sur toutes les routes, réassignation JSONB correcte pour la détection SQLAlchemy (l.83). Frontière
  « le porteur reste l'auteur » explicite (`save_draft`, l.93).
- **Résilience LLM confirmée** (`app/llm/openai_compatible.py`) : timeout par appel, `RetryPolicy`,
  `CircuitBreaker(failure_threshold=3)`, fallback — inchangée et conforme au principe 3.
