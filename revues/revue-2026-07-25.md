## Constats détaillés (nouveaux)

### Principe 4 — Tout est traçable

#### 🟠 Important — `app/sharing/service.py` : actions de partage non auditées

Trois actions sensibles du module partage **committent sans aucune trace d'audit** — le module `sharing/` **n'importe même pas** `AuditService` :

- `create_share` (`:39-59`) : génère un lien public exposant la fiche jury/incubateur d'un projet (score + synthèse + forces). C'est une **exposition volontaire de données personnelles** à un tiers non authentifié → `commit()` sans `record(...)`.
- `set_visibility` (`:87-93`) : bascule un projet en public/privé → `commit()` sans audit.
- `revoke` (`:61-67`) : coupe un partage → `commit()` sans audit.

Le référentiel classe explicitement le *partage/consentement* parmi les actions sensibles à tracer *« dans la MÊME transaction que l'action »*. Ici, le **consentement est bien horodaté** (`consent_at`) côté donnée, mais il n'existe **aucune piste d'audit** répondant à « qui a partagé quoi, quand, et quand l'a-t-il révoqué ». En cas de contestation RGPD, la trace `consent_at` sur la ligne courante ne suffit pas (elle disparaît à la révocation/suppression).

**Correction :** injecter `AuditService` dans `ShareService` (via `get_share_service`) et appeler `await self.auditor.record(actor_id=ctx.user.id, action="share.created" | "share.revoked" | "project.visibility_changed", entity="project", entity_id=project_id)` **avant** le `commit()`, dans la même transaction. C'est le patron déjà exemplaire dans `mentors/service.py` et `gdpr/service.py` (voir points conformes).

#### 🟡 Mineur — `app/gdpr/service.py:41` : l'export RGPD n'est pas audité (asymétrie avec l'effacement)

`GdprService.delete_me` (`:87`) trace correctement `user.deleted` **avant** la suppression (actor_id non contraint par FK → la trace survit). En revanche `export` (`:41-85`) — qui **rassemble et restitue l'intégralité des données personnelles** du porteur (compte, projets, bilans, documents) — ne pose **aucun** `record(...)`. La portabilité RGPD (art. 20) est pourtant une action sensible : on devrait pouvoir prouver qu'un export a eu lieu, pour qui et quand.

**Correction :** ajouter `await self.auditor.record(actor_id=u.id, action="user.data_exported", entity="user", entity_id=u.id)` + `commit()` dans `export`. (Raffine le point ouvert historique #7 « export RGPD non tracé » — désormais isolé, l'effacement, lui, est tracé.)

### Principe technique — Cohérence documentation / posture de sécurité

#### 🟡 Mineur — `app/sharing/models.py` : le docstring dément l'implémentation (token en clair persisté)

Le docstring du modèle affirme (`:3-4`) : *« Le token n'est jamais stocké en clair (hash). »* Or la table `project_shares` **persiste bien le token en clair** :

```python
token_hash: Mapped[str] = mapped_column(String(64), unique=True, index=True)
...
# Token brut pour affichage dans le dashboard porteur (risque faible : lecture publique, 90 j).
token: Mapped[str | None] = mapped_column(String(64), nullable=True, default=None)
```

Le hachage (`_hash` sha256) est donc **annulé côté défense-en-profondeur** : une fuite de la table `project_shares` expose directement tous les liens actifs, sans même avoir à casser un hash. Le compromis est **défendable** (fiche publique à faible sensibilité, TTL 90 j, révocable, `list_my_shares` a besoin de reconstruire l'URL) — mais **le docstring ment sur la posture réelle** et induira en erreur toute revue future.

**Correction :** au minimum corriger le docstring pour refléter la réalité (token brut conservé, hash utilisé pour la *lookup* et l'unicité). Mieux : ne pas persister le token en clair — afficher un préfixe masqué dans le dashboard, ou régénérer le lien à la demande.
