## Constats détaillés

### Principe 1 — Séparation en couches

#### 🟠 IMPORTANT — `app/jobs/router.py:40-52` : le router orchestre repo + audit + transaction

`retry_job` fait, dans le handler, ce qui appartient au service :

```python
repo = JobRepository(session)                 # instanciation en ligne (pas de Depends(get_job_service))
job = await repo.get_by_id(job_id)
await repo.requeue(job)
await AuditService(session).record(...)       # audit dans le router
await session.commit()                        # transaction pilotée par le router
```

Le référentiel est explicite : *« la transaction et l'audit appartiennent au service, jamais au router »*. Un `JobService` existe déjà (`app/jobs/service.py`) mais n'expose ni `retry`, ni les lectures — du coup `list_jobs` et `job_stats` instancient eux aussi `JobRepository(session)` en ligne (`:28`, `:37`).

**Correction :** ajouter au `JobService` les méthodes `retry(job_id, actor_id)` (get + requeue + `auditor.record` + commit, le tout dans `async with session.begin()`), `list_filtered(status)` et `counts_by_status()`, puis injecter le service via un provider `Depends(get_job_service)` — aligner sur le patron déjà propre de `app/scoring/router.py`.

#### 🟡 MINEUR — `app/instrumentation/router.py:23` : instanciation en ligne du service

```python
return await AnalyticsService(InstrumentationRepository(session)).learning_dashboard()
```

Le métier reste bien dans le service (pas de fuite DB dans le router), mais le câblage est fait à la main dans le handler au lieu de passer par `Depends(get_*_service)`. Signalé par le référentiel comme un signal de couche. **Correction :** extraire un `get_analytics_service(session=Depends(get_session))` et l'injecter.

### Principe 3 & 4 — I/O externe faillible / asynchronisme

#### 🟠 IMPORTANT — `app/documents/service.py:62-88` : appels réseau MinIO synchrones dans le chemin requête HTTP

`confirm_upload` et `delete` sont des méthodes `async` appelées directement depuis des routes `async` (`app/documents/router.py`), mais elles invoquent le client MinIO en **synchrone bloquant** (urllib3), sans `asyncio.to_thread`, sans timeout ni resilience :

```python
actual_size, actual_ct = self.storage.stat_object(doc.object_key)   # bloque l'event loop
...
self.storage.remove_object(doc.object_key)                          # idem
```

Sous charge, chaque appel gèle la boucle asyncio pendant tout l'aller-retour réseau (viole *« tout est asynchrone de bout en bout »* et *« tout I/O externe a un timeout »*). À noter : le pipeline de génération PDF fait déjà bien les choses (`app/diagnostics/handlers.py:211` enveloppe `put_bytes` dans `asyncio.to_thread`), la correction consiste à généraliser ce patron.

**Correction :** envelopper tout appel réseau MinIO dans `await asyncio.to_thread(...)` dans les chemins requête, borner le client par un timeout, et idéalement router ces opérations vers un job pour les traitements non critiques. Même remarque, moindre car en dégradation gracieuse, pour `pitchsim/service.py:146` (`store_deck_source` → `put_bytes` synchrone).

#### 🟡 MINEUR — `app/core/storage.py:87` : client MinIO sans timeout, storage/mailer hors `resilience`

La couche LLM est exemplaire (`app/llm/openai_compatible.py` : timeout httpx + `RetryPolicy` + `CircuitBreaker` + fallback modèle). En revanche :

- le client `Minio(...)` est créé **sans `http_client`/timeout explicite** (`:87-92`) ;
- ni MinIO ni le mailer ne passent par `app/core/resilience` (aucun `with_retry`/`CircuitBreaker`) — seul le LLM l'utilise.

Le pilier 5 demande timeout + retry + circuit breaker + mode dégradé pour **LLM, MinIO ET mailer**. Le mode dégradé est bien présent partout (best-effort, `try/except` + log) et le mailer borne son SMTP (`timeout=10`, `app/core/email.py:33`) ; il manque surtout le timeout MinIO et une stratégie de retry/CB commune. La reprise sur échec est en partie assurée en amont par la file de jobs (backoff 1/5/15 min, `max_retries=3`), ce qui atténue le risque pour les appels lancés depuis un job.

**Correction :** passer un `urllib3.PoolManager` avec timeout au constructeur `Minio`, et envelopper les appels storage/mailer critiques par `with_retry` + un `CircuitBreaker` dédié, sur le modèle du client LLM.

## Points conformes (vérifiés ce jour)

- **Séparation des couches, globalement respectée.** Aucun `repository.py` ne connaît le HTTP ; aucun `service.py` n'écrit de SQL brut (`text(...)`/`session.execute`) — l'accès données passe bien par les repositories. `app/scoring/router.py` est le patron de référence (service injecté via `Depends`).
- **Health check** (`app/platform/router.py`) : le `text("SELECT 1")` dans le router est une sonde de liveness documentée, best-effort et bornée — exception légitime, pas une fuite métier.
- **Traçabilité.** `AuditService.record(...)` est appelé dans la même transaction que l'action pour les opérations sensibles (`projects`, `mentors`, `diagnostics`, `gdpr`, retry de job).
- **Machine à états projet.** Les transitions passent par `ProjectService.change_status` avec garde `can_transition_review` (`app/projects/service.py:59`) ; `pitchsim` a sa propre garde `can_transition`. Les écritures `review_status` directes sont confinées au setter du repository appelé par le service gardé.
- **Secrets.** Tout est chargé via `app/core/config.py` en `SecretStr` (JWT, SMTP, clés LLM, MinIO) — aucun secret en dur.
- **Migrations Alembic réversibles.** Les 16 migrations possèdent toutes une fonction `downgrade`.
- **Webhooks.** `app/_v2` (paiements/signatures) n'est pas monté en phase freemium (`app/api.py`) — rien à signaler tant qu'il n'est pas câblé.
- **Résilience LLM.** Timeout + retry sur erreurs transitoires + circuit breaker par modèle + fallback inter-modèles : conforme et soigné.
