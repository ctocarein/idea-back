## Constats détaillés (nouveaux)

### Principe 3 — Tout I/O externe est faillible · file de jobs

#### 🟠 Important — Jobs orphelins en `processing` : aucune reprise possible

**`app/jobs/repository.py:44-68` (`claim_one`) · `app/worker.py:74-86` (`run`) · `app/jobs/models.py:22`**

`claim_one` bascule le job en `PROCESSING` et pose `started_at = now()` :

```sql
UPDATE jobs SET status = 'PROCESSING', started_at = now()
WHERE id = ( SELECT id FROM jobs
             WHERE status IN ('PENDING','RETRYING') AND scheduled_at <= now()
             ... FOR UPDATE SKIP LOCKED LIMIT 1 )
```

Le `SKIP LOCKED` est correct pour la concurrence entre workers, **mais rien ne récupère un job resté en `PROCESSING`** :

- aucune requête de la base de code ne sélectionne `PROCESSING` (vérifié : `grep -rn "PROCESSING" app/` ne renvoie que la déclaration d'enum et l'`UPDATE` ci-dessus) ;
- **aucun reaper / balayage de jobs périmés** n'existe (`stale`, `orphan`, `reaper` : 0 occurrence) ;
- `started_at` est écrit mais **jamais relu** — la donnée nécessaire à la détection est là, inexploitée ;
- il n'y a **ni heartbeat, ni lease, ni timeout d'exécution** par job.

Conséquence concrète : si le worker meurt en cours de traitement (crash, OOM, redéploiement, `docker compose down`), le job reste `processing` **définitivement**. `_process` ne s'exécute plus, donc ni `jobs.fail(...)` ni le `TERMINAL_REGISTRY` ne sont déclenchés — `handle_run_diagnostic_failed` (`worker.py:40`), qui est précisément le filet censé sortir un bilan de l'état d'attente, **n'est jamais appelé**. Le porteur voit un diagnostic « en cours » qui ne se terminera jamais, et le compteur `retry_count` n'a pas bougé.

La seule sortie est **manuelle** : `POST /admin/jobs/{id}/retry` (`app/jobs/router.py:40-53`, lui-même déjà signalé 🟠 pour orchestration en router). Ce n'est pas une gestion d'échec automatique au sens du Principe 3.

*Correction suggérée :* ajouter au worker un balayage périodique (toutes les N boucles) qui remet en file les jobs périmés, en réutilisant le chemin de retry existant plutôt qu'un `UPDATE` direct :

```python
# app/jobs/repository.py
async def reclaim_stale(self, *, older_than_minutes: int = 15) -> list[Job]:
    """Jobs bloqués en PROCESSING au-delà du seuil (worker mort en cours de route)."""
    stmt = (
        select(Job)
        .where(Job.status == JobStatus.PROCESSING)
        .where(Job.started_at < datetime.now(UTC) - timedelta(minutes=older_than_minutes))
    )
    return list((await self.session.execute(stmt)).scalars())
```

Côté `JobService`, les faire passer par `fail(job, TimeoutError("worker perdu"))` : le backoff, le décompte `retry_count`/`max_retries`, le `error_message` **et** le `TERMINAL_REGISTRY` (donc `handle_run_diagnostic_failed`) sont alors réutilisés tels quels, sans nouvelle logique. Le seuil devrait être configuré dans `app/core/config.py` et **supérieur à la durée du plus long job** (le diagnostic à 3 passes LLM ; cf. `llm_timeout_seconds=30 s` × passes + rendu PDF).

*Complément utile :* ajouter aussi le compte de jobs `processing` anciens à `/api/v1/health` ou aux `job_stats` (`jobs/router.py:33-37`) — un backlog silencieux doit être visible avant que le porteur ne le signale.

#### 🟠 Important — Boucle du worker sans garde : une exception tue le process

**`app/worker.py:74-86`**

```python
while True:
    async with factory() as session:
        jobs = JobService(JobRepository(session))
        job = await jobs.claim()          # ← non protégé
        if job is None:
            await asyncio.sleep(POLL_INTERVAL); continue
        logger.info("job_claimed", ...)
        await _process(job, jobs)         # ← _process protège le handler, pas jobs.fail/complete
```

`_process` (`worker.py:44-58`) capture correctement les exceptions **du handler métier** — c'est bien vu. Mais trois appels restent **hors de toute protection** :

1. `jobs.claim()` — toute erreur transitoire Postgres (reconnexion asyncpg, `OperationalError`, redémarrage de la base, coupure réseau) remonte jusqu'à `run()` ;
2. `jobs.complete(job)` (`worker.py:57`) et `jobs.fail(job, exc)` (`worker.py:52`) — si la session est en erreur ou la base indisponible **au moment d'enregistrer le verdict**, l'exception s'échappe également ;
3. `run()` n'a **aucun `try/except`** : l'exception remonte à `asyncio.run(...)` et **le process s'arrête**.

C'est la même classe de fragilité que celle déjà corrigée côté HTTP (`ratelimit.py:41` fail-open, `studio/service.py` dégradation gracieuse, `asyncio.gather(return_exceptions=True)` du scoring) : elle n'a simplement **pas été appliquée au second point d'entrée**. Et l'effet est aggravé par le constat précédent — le job en cours reste figé en `processing`, donc **la mort du worker est doublement définitive** pour ce job.

Il n'y a par ailleurs **aucun test** sur `app/worker.py` ni sur `app/jobs/*` (aucun fichier `tests/test_job*` ou `tests/*worker*`), alors que c'est le composant dont dépend tout le parcours diagnostic asynchrone.

*Correction suggérée :* envelopper le corps de boucle et ajouter un backoff sur erreur d'infrastructure, plus un arrêt propre :

```python
while not _shutdown.is_set():
    try:
        async with factory() as session:
            jobs = JobService(JobRepository(session))
            job = await jobs.claim()
            if job is None:
                await asyncio.sleep(POLL_INTERVAL); continue
            logger.info("job_claimed", job_id=str(job.id), type=job.type)
            await _process(job, jobs)
    except asyncio.CancelledError:
        raise
    except Exception as exc:  # noqa: BLE001 — la boucle ne doit jamais mourir
        logger.error("worker_loop_error", error=str(exc), exc_info=True)
        await asyncio.sleep(BACKOFF_ON_ERROR)  # ex. 5 s, éviter le hot-loop
```

Ajouter en complément un handler `SIGTERM`/`SIGINT` positionnant `_shutdown` : au redéploiement, le worker termine le job en cours au lieu d'être coupé net (ce qui est aujourd'hui la principale source de jobs orphelins). Et couvrir le tout par deux tests : « `claim` lève → la boucle survit et retente », « job orphelin `processing` ancien → remis en file ».

#### 🟡 Mineur — Client Redis créé sans timeout socket

**`app/core/cache.py:20-24`**

```python
_redis = Redis.from_url(
    settings.redis_url,
    encoding="utf-8",
    decode_responses=True,
)
```

Ni `socket_timeout`, ni `socket_connect_timeout`, ni `health_check_interval`. Le mode dégradé du rate-limit est pourtant bien pensé (`ratelimit.py:41-44` : `except` → `fail_open`, et `fail_open=False` sur les routes coûteuses LLM), **mais il ne couvre que le cas « Redis renvoie une erreur »**. Si Redis est **injoignable sans erreur** — réseau qui absorbe les paquets, instance figée, bascule d'un Redis managé — l'`await` reste pendant et **aucun `except` ne se déclenche** : la requête HTTP se bloque, pas de 429 ni de fail-open, juste une latence qui remonte jusqu'au porteur.

Sévérité mineure car le cas est plus rare qu'une panne franche et l'impact est une latence, pas une corruption ; mais le correctif est d'une ligne.

*Correction suggérée :*

```python
_redis = Redis.from_url(
    settings.redis_url,
    encoding="utf-8",
    decode_responses=True,
    socket_connect_timeout=2,
    socket_timeout=2,
    health_check_interval=30,
)
```

Deux secondes suffisent largement pour un `INCR`/`EXPIRE` local ; au-delà, mieux vaut tomber dans la branche `except` déjà écrite et laisser la politique `fail_open` trancher — ce qui rend enfin ce garde-fou effectif dans **tous** les modes de panne. Même raisonnement que le timeout client MinIO recommandé de longue date (`revue-2026-06-25.md`).
