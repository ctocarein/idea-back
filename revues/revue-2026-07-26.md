## Constats détaillés (nouveaux)

### Principe 5 — Tout I/O externe est faillible (et ne doit pas bloquer la boucle)

#### 🟠 Important — `app/documents/service.py` : appels MinIO synchrones sans `asyncio.to_thread` (blocage de l'event loop)

Le client de stockage est **synchrone par conception** — son propre docstring est sans ambiguïté :

```python
# app/core/storage.py:5
synchrone — les appelants async doivent l'invoquer via `asyncio.to_thread`.
```

Or `DocumentService` (méthodes `async`) l'appelle **en direct**, sans déport de thread :

- `confirm_upload` (`:62`) : `actual_size, actual_ct = self.storage.stat_object(doc.object_key)`
- `confirm_upload` (`:66`, `:69`) : `self.storage.remove_object(doc.object_key)` (rejet taille / type)
- `delete` (`:88`) : `self.storage.remove_object(doc.object_key)`
- `request_upload_url` (`:49`) : `storage.presigned_put(object_key)` (génération de signature — coût moindre mais même schéma)

Chaque appel `stat_object`/`remove_object` est une **I/O réseau bloquante exécutée sur la boucle asyncio** : tant que MinIO répond (ou expire), **aucune autre requête n'est servie** par ce worker. C'est l'anti-pattern que le référentiel vise au Principe 4 (*« tout est asynchrone de bout en bout »*) et au Principe 5. Le contre-exemple correct existe déjà dans le même dépôt : `platform/router.py:48` fait `await asyncio.to_thread(storage.health_ok)`.

**Aggravant :** ces appels n'ont par ailleurs ni timeout, ni retry, ni circuit breaker (dette de fond connue `storage.py`, point ouvert #4) — donc un MinIO lent fige la boucle **sans borne de temps**.

**Correction :** envelopper tous les appels MinIO du service dans `await asyncio.to_thread(...)` (a minima), ce qui débloque immédiatement la boucle ; puis, à terme, faire porter timeout/retry/circuit breaker par une façade `storage` async (résout aussi le point ouvert #4 pour `gdpr.delete_me`). Le geste `to_thread` est peu coûteux et devrait être systématisé partout où `storage` est consommé hors health check.

### Principe 4 — Tout est traçable

#### 🟡 Mineur — `app/documents/service.py:80` : suppression de document non auditée

`delete` (`:80-92`) supprime **définitivement** un document (donnée personnelle, souvent pièce jointe d'un projet : pitch, business plan) : objet MinIO retiré + ligne supprimée + `commit()`, **sans aucune trace d'audit** (`AuditService` n'est pas importé dans le module `documents/`). Une suppression de donnée personnelle est exactement le type d'action que le Principe 4 impose de tracer *« dans la MÊME transaction que l'action »*. En cas de contestation (« mon document a disparu »), il n'existe aucune piste « qui a supprimé quoi, quand ».

C'est la **même famille** que le constat `sharing/` du 25/07 : plusieurs features récentes (`sharing`, `documents`) committent des actions sensibles sans importer `AuditService`, alors que `mentors`, `gdpr`, `diagnostics`, `reports` le font correctement.

**Correction :** injecter `AuditService` dans `DocumentService` (via `get_document_service`) et poser `await self.auditor.record(actor_id=ctx.user.id, action="document.deleted", entity="document", entity_id=document_id)` **avant** le `commit()`. (Le `record` doit précéder la suppression de la ligne pour que l'`entity_id` reste cohérent ; l'`actor_id` n'étant pas contraint par FK vers le document, la trace survit.)

#### 🟡 Mineur — `app/opportunities/service.py` : mutations admin du catalogue non auditées

Les trois mutations back-office du catalogue d'opportunités **committent sans audit** :

- `admin_create` (`:85-97`), `admin_update` (`:99-117`), `admin_set_active` (`:119-125`).

Ce catalogue est **global** (visible par tous les porteurs) : créer une opportunité, en changer les seuils d'éligibilité (`min_overall`, `min_maturity`) ou la désactiver a un impact plateforme. L'absence de trace empêche de répondre à « qui a modifié / désactivé cette opportunité, et quand ». Il y a une **asymétrie** notable avec la gouvernance du scoring (`scoring/governance.py`), qui — malgré son défaut de couche connu (#1) — **audite** bien son activation.

**Correction :** injecter `AuditService` dans `OpportunityService` et tracer `opportunity.created` / `opportunity.updated` / `opportunity.activated|deactivated` dans la transaction de chaque mutation admin. Sévérité *mineure* (action admin-only, périmètre restreint), mais à aligner sur le reste du back-office pour la cohérence RGPD/gouvernance.
